# Sage 300 HR employee import and numbering reference

## Employee master import and configuration

### Takeaway
For Sage 300 People, Sage documents an Excel-based Employee Take-On workflow that can create new employee records and update existing employee data. The import is controlled by a batch header (including script, company/company rule, pay-run defaults, and update option), followed by import, verification, correction of errors, and processing; Sage warns some update options overwrite existing values, including empty fields. This is Sage 300 People guidance, not proof of equivalent behavior in the separate North American Sage 300 ERP Payroll module.

### Cited Findings
- Sage 300 People KB article “Import employee data using a take-on batch” says Employee Take-On can import new employees and update/verify existing employee data from Excel. Its steps set a unique take-on header, script and defaults, select an update option, create blank or data-populated files, import, review Broken Rules, verify, then process; it cautions that some update options overwrite existing values including empty cells. No specific Sage 300 People build is named in this article. [Sage KB: Import employee data using a take-on batch](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp%3Bjsessionid%3D709D5C87C2BC05B0345D076F39C7BE70?solutionid=200806005611213&view=print)
- Sage 300 People’s “Load a new employee” KB lists mandatory fields at employee setup: Employee, Company, Company Rule, Employee Code, Date Engaged, Date Joined Group, Leave Start, Tax Definition/Tax Status, Leave Policy, and basic identity/contact information. It further instructs linking payslip and payment-run definitions, earning lines, and (if there is no remuneration structure) earnings, deductions, employer contributions and fringe benefits. [Sage KB: Load a new employee](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=200429105315002&view=print)
- The official Sage Community Hub answer for bulk employee take-on (Sage 300 People; circa 2018) describes Utilities > Batches > Employee Take On Batch, defining a layout and mandatory definitions, exporting a populated Excel sample, importing the completed sheet, then Verify and Process and inspect Take-On Results. This supports a template-first implementation; it does not state that every optional employee detail can be imported through that batch. [Sage Community Hub: Bulk employee take on](https://communityhub.sage.com/za/sage-300-people/f/general-discussion/131840/bulk-employee-take-on)
- Sage’s Entity-vs-Employee knowledgebase note explains that entity data holds information that persists across employments (for example addresses, contacts, bank details and personal identity), while the employee record holds company-specific details such as employee code, dates, tax status, company rule, leave policy and remuneration structure. The entity code is the persistent identifier across multiple employment records. [Sage KB: Entity Management — Entity vs Employee](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?page=1&position=0&q=entity&solutionid=200428140129907)
- Sage 300 People also has specific take-on scripts (for example Employee Take On, Address Take On, Leave Take-On); the current Sage KB leave-import article says required Excel columns and leave-policy settings affect successful import, and instructs verification and review of results. [Sage KB: Import employees leave take-on using batches](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=200410132115009)

### Inferences
- A clean integration should maintain separate stable person/entity identity and employment-record/matricule identity, and should initialize company/payroll configuration before sending employee take-on rows. This follows from Sage’s entity/employee split and required company-rule/payroll links.
- Treat the Sage-generated/exported template and its selected take-on script/update option as authoritative per deployment; avoid assuming a generic CSV schema or that blank cells mean “leave unchanged,” because Sage explicitly warns that some modes overwrite with blanks.

### Gaps
- The referenced Sage 300 People KB does not expose an exhaustive, versioned field dictionary for the current Employee Take-On import or fully define the behavior of every update option. Confirm the installed People build, script, and option against its matching Sage guide before implementing field-level mapping.
- No official Sage 300 ERP North American help page confirming an equivalent employee-master import workflow was located in this research. Sage 300 ERP Payroll is a distinct product/module family; do not apply Sage 300 People steps to it without checking its own version help.

## Employee numbering and code changes

### Takeaway
In Sage 300 People, employee code is a required, company-specific employment-record identifier and Sage KB guidance describes changing it one employee at a time, with strict format and downstream Self Service considerations. An entity code is conceptually different and remains the person’s persistent identifier across employment records. Official Sage Community Hub guidance says Sage 300 People does not automatically allocate employee codes; this is a community answer rather than a versioned product specification.

### Cited Findings
- Sage’s KB “Modifying an employee code in payroll” states that the code can be changed one at a time; maximum eight characters; alphanumeric only; avoid lowercase, spaces, special characters, and reusing old codes. It says to clear active Sage Self Service workflow transactions and synchronize leave transactions/balances first, take a full company backup, then use Main Menu > Employee > Modify Employee Number and confirm the change. The article explicitly says the system does not support bulk employee-code changes. Product screen terminology in the article is “Employee / Modify Employee Number”; no product build number is supplied. [Sage KB: Modifying an employee code in payroll](https://za-kb.sage.com/portal/app/portlets/results/botviewsolution.jsp?hypermediatext=null&solutionid=200524190253410)
- The same Sage KB article warns that changing the employee code for an employee linked to Sage Self Service generates a new GUID; the new employee profile must be uploaded, the old profile deleted, and the new profile linked to workflow. [Sage KB: Modifying an employee code in payroll](https://za-kb.sage.com/portal/app/portlets/results/botviewsolution.jsp?hypermediatext=null&solutionid=200524190253410)
- Sage’s Entity-vs-Employee KB states employee code normally identifies an employee record and may change when a person has multiple records, while the entity code is the unique identifier throughout employment. [Sage KB: Entity Management — Entity vs Employee](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?page=1&position=0&q=entity&solutionid=200428140129907)
- In Sage Community Hub, a Sage 300 People discussion asks about automatic employee code assignment; the reply says Sage 300 People does not assign employee codes automatically (and mentions a third-party generator). The forum post is undated in product-version terms and the answer is not a formal KB article, so treat it as corroboration, not a universal release guarantee. [Sage Community Hub: Employee auto numbering](https://communityhub.sage.com/za/sage-300-people/f/general-discussion/202326/employee-auto-numbering)
- A Sage 300 People release announcement for version 22.4.3.0, released 7 December 2022, lists API support for employee code changes and linking to an existing entity code. This is an API feature in that release note, not evidence of automatic numbering or bulk code change. [Sage Community Hub: Sage 300 People V22.4.3.0 release announcement](https://communityhub.sage.com/za/sage-300-people/f/announcements/193722/software-update-v22-4-3-0---sage-300-people)

### Inferences
- For a future HR system, define a unique matricule policy outside Sage People and submit explicit codes in employee-create/take-on requests; preserve a separate stable person identifier to handle rehires or employment records where codes differ.
- Avoid designing a bulk rename feature that assumes code mutation is supported as a batch operation. A safer operational model is individual code changes with a reviewed migration procedure, or API availability only after verifying the target version’s current API contract and integration impacts.

### Gaps
- Sage’s Community response says no automatic employee-code allocation but is not pinned to a build. Check the deployed release and any licensed/add-on capabilities.
- The 22.4.3.0 note establishes that an API feature existed in that release, but the research did not retrieve its endpoint schema, authorization requirements, collision rules, or current support status.

## Bulk actions and change workflows

### Takeaway
Sage 300 People distinguishes bulk field updates from employee-code renaming. For routine employee changes it offers Bulk Employee Update, system-defined batch files, and user-defined batches; workflows generally select/filter records, import or apply changes, verify, process, and inspect results. Employee code changes remain one-at-a-time according to Sage’s KB.

### Cited Findings
- Sage KB “Apply a bulk employee increase” documents Utilities > Bulk Employee Update > Increase: filter employee list, remove employees who should not receive the change, confirm the selected count, complete required fields and review results. The effective increase applies in the current period; a past effective date is reporting-only and does not backdate the increase. Product: Sage 300 People; KB article originally published 22 May 2020 and last modified 8 December 2025. [Sage KB: Apply a bulk employee increase](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=200522112348404)
- Sage Community Hub instructions for Positions Batch describe exporting selected positions to Excel, editing rows, importing a new batch with Batch Option set to Update, then verifying and processing. This is a system-defined Positions Batch example, not a universal employee-field update contract. [Sage Community Hub: How do I do bulk changes to my Positions](https://communityhub.sage.com/za/sage-300-people/f/general-discussion/126995/how-do-i-do-bulk-changes-to-my-positions-on-the-system)
- Sage Community Hub says bulk employee updates such as linking employees to a calculation can filter by company rule/status, refresh and search, confirm the number selected, and use either a full update mode or a criteria-based mode. The example is specifically the Link Calculations action. [Sage Community Hub: Bulk link employees to linked calculation](https://communityhub.sage.com/za/sage-300-people/f/general-discussion/110143/bulk-link-employees-to-linked-calculation)
- Sage Community Hub describes user-defined batches for bulk updating a field not supported by the employee take-on workflow (example: Remuneration Definition Header); the specified field must be included in the user-defined batch. [Sage Community Hub: Remuneration Definition Header](https://communityhub.sage.com/za/sage-300-people/f/general-discussion/179414/remuneration-definition-header)
- Sage’s “Modifying an employee code in payroll” KB states code changes are one at a time and no bulk employee-code-change option is supported. [Sage KB: Modifying an employee code in payroll](https://za-kb.sage.com/portal/app/portlets/results/botviewsolution.jsp?hypermediatext=null&solutionid=200524190253410)
- Sage’s audit-detail KB says Audit > Detail can be filtered by pay period, table, employee code, username and date range, and exported; results include user, effective date and old/new values. This is useful as an implementation/reconciliation analog for auditable bulk updates. [Sage KB: View audit details](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=200405165247504)
- For the separate Sage 300 ERP Payroll integration product, Sage’s Sage Payroll Link integration guide describes Sage HRMS Process choices for syncing Time Off, Pay Information, Benefits or Update All based on field mapping configured in Employee Configuration. It recommends limiting the updates to needed records for speed, while Update All is useful after substantial mapping changes. This applies to Sage HRMS Payroll Link / Sage 300 Payroll integration, not Sage 300 People. [Sage Payroll Link Integration Guide (PDF)](https://communityhub.sage.com/cfs-file/__key/communityserver-discussions-components-files/137/Sage300Payroll_5F00_SageHRMS_5F00_IntegrationGuide.pdf)

### Inferences
- Model bulk mutation with a saved target selection, explicit preview/count, validation, a distinct process/commit step, and per-row outcomes; this mirrors documented People workflows and helps prevent silent partial updates.
- Keep employee-code changes behind an individually auditable path separate from general bulk field updates because Sage treats them differently and documents Self Service effects.
- Where a synchronized Sage 300 ERP Payroll deployment is in scope, configuration mapping governs which HR changes move across; configuration changes may require a broad synchronization according to the integration guide.

### Gaps
- The Sage 300 ERP search results found general payroll module and table documentation but not official documentation for importing/updating the employee master in the current ERP Payroll build. Do not extrapolate Sage 300 People’s Excel batch capability to ERP Payroll. Obtain version-specific in-product help or Sage support documentation for that module.
- The accessible Sage Payroll Link guide is published around 2019/2017. Verify supported screens and scheduling behavior against the installed Sage HRMS and Sage 300 Payroll versions.
